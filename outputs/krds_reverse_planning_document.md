# KRDS 웹사이트 및 디자인 시스템 역기획서

작성일: 2026-06-09  
문서 목적: KRDS 공식 웹사이트, GitHub, Figma Community 공개 자료를 바탕으로 원 기획 의도와 화면/컴포넌트 요구사항을 역으로 정리한다.

### 1.2 근거 기반 사실

KRDS는 대한민국 디지털 정부 서비스의 편의성, 일관성, 접근성, 사용성을 보장하기 위해 설계된 디자인 시스템이며, 공공 웹사이트와 애플리케이션에서 일관된 UX/UI를 제공하고 다양한 디지털 정부 서비스의 표준화를 목적으로 한다.

KRDS는 디자인 라이브러리, 디자인 토큰, HTML Component Kit, 문서화 웹사이트를 하나의 운영 구조로 연결한다. 디자이너용 Figma 라이브러리는 스타일 가이드, 컴포넌트, 기본 패턴, 서비스 패턴, 아이콘 페이지로 구성되고, 로컬 변수와 로컬 스타일을 통해 토큰 구조를 확인할 수 있다.

개발자용 산출물은 HTML Component Kit, NPM 패키지, GitHub 다운로드, CDN, SCSS/CSS, JavaScript, React/Vue 연계, 디자인 토큰 JSON 추출 및 CSS variable 변환을 포함한다. GitHub package.json 기준 `krds-uiux` 버전은 `1.1.0`이다.

### 1.3 해석상 주의점

공식 컴포넌트 목록 페이지에는 `총 37건`으로 표기되어 있으나, 디자이너 시작하기 문서는 Figma 라이브러리에 `컴포넌트 43종의 모든 변형`을 제공한다고 설명한다. 본 문서는 웹사이트 문서화 범위와 Figma 자산 범위가 다를 수 있다고 보고, 화면 요구사항은 공식 웹 문서 기준, Figma 제작 요구사항은 Figma 라이브러리 기준으로 작성한다.

## 2. 프로젝트 개요

### 2.1 프로젝트명

KRDS Korea Design System 웹사이트 및 HTML/Figma 디자인 시스템 구축

### 2.2 한 줄 정의

공공 디지털 서비스 제작자가 같은 언어와 같은 자산으로 설계, 개발, 운영할 수 있도록 하는 정부 서비스 표준 UX/UI 플랫폼.

### 2.3 배경 문제

공공 디지털 서비스는 기관별로 유사한 과업을 반복해서 구현하지만, 화면 구조, 컴포넌트 상태, 접근성 대응, 용어, 디자인 토큰, 코드 구현 방식이 흩어질 경우 국민 입장에서는 서비스마다 새로운 사용법을 학습해야 한다.

디자이너와 개발자는 같은 버튼, 입력 필드, 로그인, 신청, 검색 화면을 매번 새로 설계하거나 구현하게 되고, 정부 관계자는 구축 사업의 품질 검수 기준을 일관되게 판단하기 어렵다. KRDS는 이러한 문제를 디자인 라이브러리, 토큰, 컴포넌트 키트, 가이드 문서, 적용 사례로 해결하려는 시스템이다.

### 2.4 핵심 목표

- 국민에게 예측 가능하고 접근 가능한 디지털 정부 서비스 경험을 제공한다.
- 디자이너, 개발자, 정부 관계자의 협업 언어를 디자인 토큰과 컴포넌트 기준으로 통일한다.
- 공공 서비스 구축 시 반복되는 UI 제작 비용과 검수 비용을 낮춘다.
- 기관별 확장성을 허용하되 접근성, 반응형, 사용성 기준은 흔들리지 않게 한다.
- Figma, HTML/CSS/JS, GitHub, NPM, 문서 웹사이트를 연결한 운영형 디자인 시스템으로 관리한다.

## 3. 타깃 사용자와 요구

### 3.1 디자이너

주요 니즈:

- Figma에서 바로 가져다 쓸 수 있는 스타일, 변수, 컴포넌트, 패턴이 필요하다.
- 표준형과 확장형 스타일을 구분하고, 기관별 색상/타이포그래피/형태 변경 시 어떤 토큰을 건드려야 하는지 알아야 한다.
- 상태, 크기, 반응형, 선명한 화면 모드, 접근성 기준을 매 화면에서 반복 검토하지 않고 컴포넌트 속성으로 처리하고 싶다.

핵심 성공 조건:

- Figma 자산 검색이 쉬워야 한다.
- 컴포넌트 variant와 property가 실제 사용 언어로 정리되어야 한다.
- 화면 설계자가 서비스 패턴을 복제해 실제 과업 화면을 빠르게 만들 수 있어야 한다.

### 3.2 개발자

주요 니즈:

- HTML Component Kit을 NPM, GitHub, CDN으로 설치할 수 있어야 한다.
- Figma 토큰 JSON을 CSS variable로 변환하는 흐름이 명확해야 한다.
- SCSS 원본과 컴파일 CSS를 모두 활용할 수 있어야 한다.
- React/Vue 환경에서 컴포넌트를 적용할 수 있어야 한다.

핵심 성공 조건:

- 코드 예제와 실제 동작 예제가 함께 제공되어야 한다.
- 컴포넌트별 접근성, 키보드 상호작용, 상태 클래스가 명확해야 한다.
- 원본 토큰을 직접 수정하지 않고 프로젝트 레벨에서 재선언할 수 있어야 한다.

### 3.3 정부 관계자 및 발주/검수자

주요 니즈:

- KRDS 적용 범위와 의무/권장 수준을 이해해야 한다.
- 구축 사업에서 어떤 화면과 컴포넌트를 표준 기준으로 검수해야 하는지 확인해야 한다.
- 디지털 포용, 접근성, 사용자 피드백, 적용 사례를 근거로 품질을 판단해야 한다.

핵심 성공 조건:

- 비전문가도 이해할 수 있는 역할별 진입점이 있어야 한다.
- 체크리스트와 적용 사례가 실제 사업 검수에 연결되어야 한다.
- 문의 및 건의 채널이 운영되어야 한다.

## 5. 정보 구조

### 5.1 1차 내비게이션

KRDS 웹사이트의 1차 구조는 다음과 같이 역기획된다.

| 메뉴 | 목적 | 핵심 콘텐츠 |
|---|---|---|
| 시작하기 | 사용자 역할별 온보딩 | KRDS 시작하기, 디자이너, 개발자, 정부 관계자, 리소스 다운로드 |
| 디자인 스타일 | 시각/토큰 기준 제공 | 색상, 타이포그래피, 형태, 레이아웃, 아이콘, 엘리베이션, 선명한 화면 모드, 디자인 토큰 |
| 컴포넌트 | UI 최소 단위 제공 | 아이덴티티, 탐색, 레이아웃 및 표현, 액션, 선택, 피드백, 도움, 입력, 설정, 콘텐츠 |
| 기본 패턴 | 반복 과업 UI 조합 제공 | 개인 식별 정보 입력, 도움, 동의, 목록 탐색, 사용자 피드백, 상세 정보 확인, 오류, 입력 폼, 첨부파일, 필터링/정렬, 확인 |
| 서비스 패턴 | 사용자 여정 기반 표준 프로토타입 | 방문, 검색, 로그인, 신청, 정책 정보 확인 |
| 소식·소통 | 운영 커뮤니케이션 | 새소식, FAQ, 적용 사례, 자료실, 문의 및 건의 |
| KRDS 소개 | 목적과 원칙 설명 | 소개, UI/UX 가이드라인, 디자인 원칙, 네이밍 원칙, 디지털 포용, 이용 안내, 저작권 |

### 5.2 정보 구조 설계 원칙

- 역할별 진입과 산출물별 진입을 모두 제공한다.
- 문서 탐색은 깊이가 있어도 현재 위치를 잃지 않도록 브레드크럼, 사이드 메뉴, 콘텐츠 내 탐색을 제공한다.
- 메인 페이지는 비전 전달보다 실무자 진입 속도를 우선한다.
- 컴포넌트와 패턴은 검색, 필터, 카테고리로 접근해야 한다.
- Figma, GitHub, 리소스 다운로드는 문서 하단 보조 링크가 아니라 주요 업무 경로로 취급한다.

## 6. 사용자 여정

### 6.1 디자이너 온보딩 여정

1. 메인 페이지에서 `디자이너` 진입
2. Pretendard GOV 서체 준비
3. Figma Community의 KRDS 라이브러리 열기 또는 복제
4. 파일 페이지 구조 확인: 스타일 가이드, 컴포넌트, 패턴, 아이콘
5. 로컬 변수와 스타일 확인
6. 필요한 컴포넌트를 Assets에서 검색
7. 컴포넌트 property와 variant 변경
8. 기본 패턴 또는 서비스 패턴을 화면 설계에 적용
9. 기관별 확장이 필요한 경우 primitive/semantic token 변경 영향 검토
10. 접근성, 선명한 화면 모드, 반응형 모드 검수

### 6.2 개발자 온보딩 여정

1. 메인 페이지에서 `개발자` 진입
2. HTML Component Kit 설치 방식 선택: NPM, GitHub, CDN
3. Pretendard GOV 웹폰트 설정
4. SCSS/CSS import 방식 결정
5. 컴포넌트 마크업과 JS 상호작용 적용
6. Figma 토큰 JSON을 CSS variable로 변환
7. 프로젝트 레벨에서 필요한 토큰 재선언
8. 접근성 및 키보드 상호작용 검수
9. React/Vue 환경이면 별도 패키지/문서 확인

### 6.3 정부 관계자/검수자 여정

1. 메인 페이지에서 `정부 관계자` 진입
2. KRDS 목적, 필요성, 구성 요소 확인
3. 디지털 포용 및 접근성 기준 확인
4. 적용 사례 확인
5. 사업 산출물에서 컴포넌트/패턴 적용 여부 점검
6. FAQ와 문의 채널을 통해 적용 이슈 해결

## 7. 기능 요구사항

### 7.1 공통 기능

| 기능 | 요구사항 | UX 기준 |
|---|---|---|
| 공식 전자정부 배너 | 모든 페이지 최상단에서 공식 서비스임을 식별한다. | 사용자가 서비스 신뢰성을 즉시 판단할 수 있어야 한다. |
| 본문 바로가기 | 키보드 사용자가 반복 내비게이션을 건너뛸 수 있게 한다. | 포커스 진입 시 명확히 노출되어야 한다. |
| 통합검색 | 메뉴명, 컴포넌트명, 패턴명, 문서 내용을 검색한다. | 검색어 입력, 결과 없음, 닫기, 키보드 조작을 지원한다. |
| 전체메뉴 | 전체 IA를 한 화면에서 탐색한다. | 카테고리 구조와 현재 위치를 명확히 보여준다. |
| 글자·화면 설정 | 글자 크기와 화면 표시 모드를 조정한다. | 작게, 보통, 조금 크게, 크게, 가장 크게와 기본/선명/시스템 설정을 제공한다. |
| 언어 변경 | 한국어와 English 전환 경로를 제공한다. | 헤더에서 발견 가능해야 한다. |
| GitHub/Figma 링크 | 개발/디자인 자산으로 빠르게 이동한다. | 푸터뿐 아니라 관련 문서 본문에도 제공한다. |
| 문의 및 건의 | 개선 의견과 적용 이슈를 접수한다. | FAQ 확인 후 문의로 이어지는 흐름을 제공한다. |

### 7.2 검색 기능

요구사항:

- 헤더에서 항상 접근 가능해야 한다.
- 검색 모달 또는 검색 레이어는 닫기 버튼과 Esc 닫기를 지원해야 한다.
- 입력 필드는 명확한 레이블과 플레이스홀더를 가져야 한다.
- 검색 결과는 메뉴, 문서, 컴포넌트, 패턴, 리소스 유형을 구분해 제공하는 것이 바람직하다.
- 결과 없음 상태는 맞춤법 확인, 검색어 분리, 더 일반적인 단어 사용을 안내한다.

검수 기준:

- 키보드만으로 열기, 입력, 검색, 결과 이동, 닫기가 가능하다.
- 검색 레이어가 열렸을 때 포커스는 검색 입력 또는 닫기 버튼으로 이동한다.
- 결과 항목은 링크 목적을 스크린 리더가 이해할 수 있는 이름으로 제공한다.

### 7.3 글자·화면 설정

요구사항:

- 글자 크기 단계는 최소 5단계를 제공한다.
- 화면 표시 모드는 기본, 선명하게, 시스템 설정을 제공한다.
- 설정 변경은 현재 페이지에서 즉시 반영되어야 한다.
- 초기화 기능을 제공해야 한다.
- 설정 값은 세션 또는 로컬 저장소에 저장하는 것을 권장한다.

검수 기준:

- 글자 크기를 최대로 키워도 헤더, 버튼, 탭, 카드, 표 텍스트가 겹치지 않는다.
- 선명한 화면 모드에서 배경, 텍스트, 아이콘, 보더 대비가 유지된다.
- 시스템 설정 선택 시 OS 또는 브라우저 색상 선호 설정과 충돌하지 않는다.

## 8. 화면 요구사항

### 8.1 공통 레이아웃 Shell

목적:

모든 KRDS 문서 화면의 신뢰성, 탐색성, 접근성을 보장하는 기본 골격이다.

필수 구성:

- 공식 전자정부 배너
- 본문 바로가기 링크
- 언어 변경
- 글자·화면 설정
- KRDS 로고
- 통합검색
- 전체메뉴
- 1차 내비게이션
- 브레드크럼
- 좌측 사이드 메뉴 또는 문서 내 탐색
- 본문 영역
- 문의/FAQ CTA
- 구버전 사이트 안내
- 푸터: 연락처, 이메일, 문의, GitHub, Figma, 소개, 이용 안내, 저작권

상호작용:

- 헤더 메뉴는 마우스, 터치, 키보드에서 동일하게 접근 가능해야 한다.
- 메뉴가 열린 상태에서 외부 클릭, Esc, 닫기 버튼으로 닫을 수 있어야 한다.
- 현재 메뉴와 현재 페이지는 시각적으로 구분되고 보조기술에도 전달되어야 한다.
- 스크롤이 긴 문서에서는 콘텐츠 내 탐색을 고정 또는 근접 배치한다.

반응형:

- 데스크톱: GNB와 사이드 메뉴를 병행한다.
- 태블릿: GNB의 밀도를 낮추고 전체메뉴 접근성을 강화한다.
- 모바일: 핵심 액션은 헤더에 유지하되, 사이드 메뉴는 드로어 또는 페이지 내 목차로 전환한다.

접근성:

- 헤더와 내비게이션은 landmark 역할을 명확히 한다.
- 현재 페이지에는 `aria-current`에 해당하는 의미가 있어야 한다.
- 키보드 포커스 순서는 공식 배너, 본문 바로가기, 헤더, 본문 순으로 자연스러워야 한다.

### 8.2 메인 페이지

목적:

KRDS의 비전과 주요 진입 경로를 1화면 안에서 이해시키고, 역할별 시작 경로로 빠르게 유도한다.

필수 구성:

- 히어로 메시지: 모두를 위한 디지털 서비스 경험
- 시작하기 섹션: 디자이너, 개발자, 정부 관계자
- 역할별 카드: 튜토리얼, 리소스, 디자인 토큰 또는 개발 리소스
- 주요 구성: 디자인 원칙, 디지털 포용, 스타일, 컴포넌트, 기본 패턴, 서비스 패턴
- 디자인 적용 사례
- FAQ 미리보기
- 문의 및 건의 CTA

UX 설계 기준:

- 히어로는 브랜드 선언보다 사용자가 무엇을 해야 하는지 알 수 있게 구성한다.
- 역할 탭/세그먼트는 사용자가 자신을 빠르게 식별할 수 있어야 한다.
- 주요 구성 카드는 각각 시스템 안에서 맡는 역할을 설명해야 한다.
- 적용 사례는 KRDS가 실제 서비스에 적용되었다는 신뢰 근거가 되어야 한다.

검수 기준:

- 첫 화면에서 KRDS의 목적, 대상 사용자, 시작 버튼이 모두 확인된다.
- 역할 전환 시 콘텐츠가 크게 흔들리거나 스크롤 위치가 예측 불가능하게 변하지 않는다.
- 카드 제목과 설명은 클릭 후 이동할 페이지와 정확히 대응한다.

### 8.3 디자이너 시작하기 화면

목적:

Figma 라이브러리를 기반으로 KRDS를 설계 업무에 적용하는 절차를 제공한다.

필수 구성:

- 문서 목적 설명
- 튜토리얼 영역
- Figma 라이브러리 설명
- 부가 리소스 Sketch/XD 안내
- Pretendard GOV 서체 준비
- Figma Community 파일 열기
- 파일 구성 안내: 스타일 가이드, 컴포넌트, 패턴, 아이콘
- 로컬 변수, 로컬 스타일 확인 방법
- Assets 검색과 컴포넌트 배치 방법
- variant/property 변경 방법
- 라이브러리 게시 및 파일 추가
- 토큰 사용하기

UX 설계 기준:

- 초보자는 순서대로 따라 할 수 있고, 숙련자는 필요한 섹션으로 바로 이동할 수 있어야 한다.
- Figma 화면 캡처는 실제 인터페이스의 위치 감각을 제공해야 한다.
- 텍스트는 절차형으로 작성하되, 왜 필요한지 짧게 설명한다.

검수 기준:

- `서체 다운로드`, `Figma 파일 열기`, `컴포넌트 배치`, `변형 변경`, `라이브러리 게시`가 독립 단계로 확인된다.
- Figma에서 사용하는 용어와 웹 문서 용어가 일치한다.
- 각 단계에는 실패했을 때 확인할 수 있는 보조 링크 또는 FAQ가 연결된다.

### 8.4 개발자 시작하기 화면

목적:

HTML Component Kit을 프로젝트에 설치하고, 디자인 토큰과 코드 구현을 연결하는 절차를 제공한다.

필수 구성:

- 튜토리얼
- Pretendard GOV 웹폰트 CDN 안내
- HTML Component Kit 설치: NPM, GitHub, CDN
- React/Vue 설치 및 Storybook 링크
- 디자인 토큰 JSON 추출
- CSS variable 변환
- SCSS/CSS 스타일 사용자화
- 개별 컴포넌트 import
- JavaScript 사용
- 디자인 토큰 수정 주의사항
- FAQ와 문의 경로

UX 설계 기준:

- 코드 블록은 복사 가능한 형식이어야 한다.
- NPM/GitHub/CDN 방식은 선택 기준을 함께 제공해야 한다.
- 토큰 수정은 원본 수정 금지, 프로젝트 레벨 재선언 원칙을 명확히 알려야 한다.

검수 기준:

- 설치 방식별 최소 실행 예제가 있다.
- SCSS 경로 복제 및 참조 경로 재설정 주의사항이 누락되지 않는다.
- 컴포넌트별 JS 의존성이 있는 경우 명시된다.

### 8.5 정부 관계자 시작하기 화면

목적:

KRDS 적용 필요성, 적용 범위, 검수 기준, 운영 문의 경로를 비전문가도 이해할 수 있게 제공한다.

필수 구성:

- KRDS 필요성
- 표준형/확장형 스타일 개념
- 구축 사업에서 확인해야 할 산출물
- 디자인 시스템 구성 요소
- 접근성 및 디지털 포용 핵심 기준
- 적용 사례
- 문의 및 건의

UX 설계 기준:

- 기술 용어는 필요한 수준으로만 사용한다.
- 정책/사업 담당자가 문서를 근거로 의사결정할 수 있게 체크리스트 중심으로 구성한다.
- 적용 사례는 기관명, 적용 패턴, 효과를 함께 보여주는 것이 바람직하다.

### 8.6 디자인 스타일 화면

목적:

컴포넌트와 패턴을 일관되게 표현하기 위한 시각 기준을 제공한다.

하위 화면:

- 색상
- 타이포그래피
- 형태
- 레이아웃
- 아이콘
- 엘리베이션
- 선명한 화면 모드
- 디자인 토큰

공통 요구사항:

- 각 스타일 요소는 정의, 사용 기준, Do/Don't, Figma 토큰/스타일명, CSS variable 연결을 제공한다.
- 반응형과 선명한 화면 모드에서 값이 달라지는 요소는 반드시 별도 표기한다.
- 기관 확장 시 수정 가능한 요소와 수정하면 안 되는 요소를 구분한다.

### 8.7 디자인 토큰 화면

목적:

디자인 속성을 변수화해 Figma와 코드 간 일관성을 유지하는 토큰 구조를 설명한다.

필수 구성:

- 디자인 토큰 정의
- 토큰 사용 이유: 일관성, 협업, 접근성 및 표준화
- 토큰 흐름: Figma 토큰 JSON 추출, CSS variable 변환, HTML 적용
- 토큰 레벨: primitive, semantic, component
- 시멘틱 토큰 표기
- 컴포넌트 토큰 표기
- 모드 전환: 기본/선명한 화면 모드, responsive large/small
- 전체 토큰 보기

UX 설계 기준:

- 토큰 구조는 다이어그램으로 제공한다.
- 토큰 예시는 실제 CSS variable과 Figma variable을 함께 보여준다.
- 컴포넌트 토큰은 코드에서 관리한다는 역할 분리를 명확히 한다.

검수 기준:

- Figma Local Variable의 collection/mode 명칭 생략 규칙이 문서화되어 있다.
- JSON 내보내기 시 px에서 rem으로 변환되는 원칙이 안내되어 있다.
- `--krds` namespace 사용 방식이 명확하다.

### 8.8 컴포넌트 목록 화면

목적:

KRDS 컴포넌트를 검색하고 유형별로 탐색하는 허브를 제공한다.

필수 구성:

- 컴포넌트 정의
- 컴포넌트명 검색
- 유형 필터: 전체, 아이덴티티, 입력, 도움, 피드백, 선택, 액션, 레이아웃 및 표현, 탐색, 모바일
- 총 개수 표기
- 컴포넌트 카드 또는 목록
- 결과 없음 상태

UX 설계 기준:

- 목록형과 카드형 중 정보 밀도에 맞는 표현을 선택한다. 문서형 서비스에서는 검색성과 스캔성이 우선이다.
- 컴포넌트 항목은 한글명, 영문명, 요약 설명, 유형을 포함한다.
- 유형 필터는 선택 상태가 명확해야 하고, URL 또는 상태 저장이 되면 좋다.

검수 기준:

- 컴포넌트 검색어 입력 후 결과가 즉시 갱신되거나 명확한 검색 버튼이 제공된다.
- 결과 없음 상태는 사용자가 다음 행동을 알 수 있게 안내한다.
- 필터 선택 시 스크린 리더가 선택 상태를 알 수 있다.

### 8.9 컴포넌트 상세 화면

목적:

각 컴포넌트의 역할, 사용 기준, 변형, 상태, 상호작용, 접근성, 코드 구현 기준을 제공한다.

권장 템플릿:

1. 컴포넌트명: 한글명, 영문명
2. 요약 정의
3. 사용 시점
4. 사용하지 말아야 할 시점
5. 구성 요소
6. 유형 및 변형
7. 크기
8. 상태
9. 상호작용
10. 접근성
11. 콘텐츠 작성 기준
12. 반응형 기준
13. 선명한 화면 모드 기준
14. Figma property
15. HTML/CSS/JS 코드
16. 관련 컴포넌트와 패턴

상태 기준:

- enabled
- hover
- pressed
- focus
- disabled
- selected
- expanded/collapsed
- loading
- error
- success
- readonly
- required
- high-contrast
- responsive large/small

검수 기준:

- 상태명이 Figma, 문서, 코드에서 동일하거나 대응표가 제공된다.
- 키보드 조작과 포커스 이동이 빠짐없이 설명된다.
- 컴포넌트가 단독 사용인지 패턴 일부인지 구분된다.

### 8.10 기본 패턴 화면

목적:

반복되는 공공 서비스 과업 UI를 컴포넌트 조합 단위로 제공한다.

패턴 범위:

- 개인 식별 정보 입력
- 도움
- 동의
- 목록 탐색
- 사용자 피드백
- 상세 정보 확인
- 오류
- 입력 폼
- 첨부파일
- 필터링·정렬
- 확인

요구사항:

- 각 패턴은 사용자 과업, 포함 컴포넌트, 화면 구조, 상태, 예외 케이스를 함께 제공한다.
- 패턴은 단순 UI 조합이 아니라 사용자가 과업을 완료하는 흐름으로 설명한다.
- 입력/오류/확인 계열 패턴은 접근성 기준과 스크린 리더 안내를 포함한다.

### 8.11 서비스 패턴 화면

목적:

디지털 정부서비스 핵심 과업을 사용자 여정 기반 표준 프로토타입으로 제공한다.

패턴 범위:

- 방문
- 검색
- 로그인
- 신청
- 정책 정보 확인

요구사항:

- 각 서비스 패턴은 사용자 진입, 탐색, 판단, 입력, 확인, 완료 흐름을 포함한다.
- 로그인은 인지 기능 테스트에 의존하지 않는 인증 방식, 자동완성, 논리적 초점 순서를 고려한다.
- 신청은 단계 표시기, 신청서 섹션 제목, 체크박스 레이블, 저장/공유/제출 액션의 접근 가능한 이름을 포함한다.
- 정책 정보 확인은 탐색, 필터, 상세 확인, 공유/저장 흐름을 포함한다.

## 9. 컴포넌트 요구사항

### 9.1 컴포넌트 설계 원칙

- 컴포넌트는 가장 작은 재사용 단위이며, 과업과 무관하게 일관되게 사용되어야 한다.
- 컴포넌트는 상태, 역할, 변형, 사용성, 접근성, 상호작용, 플랫폼 고려 사항을 포함해야 한다.
- 변형은 시각적 모양이 아니라 역할과 사용 맥락을 기준으로 정의한다.
- Figma variant/property, 문서명, CSS class, JS 상태명이 서로 대응되어야 한다.
- 컴포넌트는 단독 사용, 패턴 내 사용, 서비스 패턴 내 사용 시의 차이를 설명해야 한다.

### 9.2 Figma 컴포넌트 속성 체계

권장 property:

| Property | 예시 값 | 적용 대상 |
|---|---|---|
| Type | primary, secondary, tertiary, danger, text | 버튼, 링크, 배지, 알림 |
| Size | xsmall, small, medium, large, xlarge | 버튼, 입력, 태그, 배지 |
| State | enabled, hover, pressed, focus, disabled, error, success | 모든 인터랙션 컴포넌트 |
| Icon | none, leading, trailing, only | 버튼, 링크, 입력 |
| Required | true, false | 입력 계열 |
| Selected | true, false | 선택 계열 |
| Expanded | true, false | 아코디언, 디스클로저, 메뉴 |
| Mode | light, high-contrast | 전체 컴포넌트 |
| Responsive | large, small | 반응형 대응 컴포넌트 |
| Platform | web, mobile | 공통/모바일 컴포넌트 |

### 9.3 아이덴티티 컴포넌트

대상:

- 공식 배너
- 운영기관 식별자
- 헤더
- 푸터

요구사항:

- 서비스의 공식성, 운영 주체, 브랜드 신뢰를 제공한다.
- 헤더는 통합검색, 전체메뉴, 주요 내비게이션을 포함한다.
- 푸터는 사용자가 원하는 정보를 찾지 못했거나 탐색 중 길을 잃었을 때 보조 탐색과 문제 해결 링크를 제공한다.
- 운영기관 식별자는 공식 배너, 푸터와 함께 서비스 운영 주체를 명확히 드러낸다.

상태/반응형:

- 헤더 메뉴 열림/닫힘
- 검색 열림/닫힘
- 전체메뉴 열림/닫힘
- 모바일 메뉴 전환
- 고대비 모드

접근성:

- 공식 배너는 반복 콘텐츠이므로 본문 바로가기와 충돌하지 않아야 한다.
- 헤더 로고는 홈 이동 링크로 동작하되 접근 가능한 이름을 제공한다.
- 푸터 링크는 목적을 구체적으로 드러내야 한다.

### 9.4 탐색 컴포넌트

대상:

- 건너뛰기 링크
- 메인 메뉴
- 브레드크럼
- 사이드 메뉴
- 콘텐츠 내 탐색
- 페이지네이션
- 링크

요구사항:

- 현재 위치, 상위 구조, 다음 이동 가능성을 동시에 제공한다.
- 문서형 사이트에서는 사이드 메뉴와 콘텐츠 내 탐색이 긴 본문을 보조한다.
- 페이지네이션은 많은 목록을 나누되 사용자가 전체 위치를 이해할 수 있게 한다.

키보드 기준:

- Tab 순서가 시각적 순서와 일치한다.
- 메뉴 열림 후 첫 항목 또는 닫기 버튼으로 포커스가 이동한다.
- 브레드크럼은 현재 항목을 링크가 아닌 현재 위치로 표시할 수 있다.
- 페이지네이션의 현재 페이지는 명확한 선택 상태를 가진다.

### 9.5 레이아웃 및 표현 컴포넌트

대상:

- 구조화 목록
- 긴급 공지
- 달력
- 디스클로저
- 모달
- 배지
- 아코디언
- 이미지
- 캐러셀
- 탭
- 표
- 텍스트 목록
- 파비콘

요구사항:

- 많은 정보를 사용자가 훑고 비교하고 집중할 수 있도록 구조화한다.
- 모달은 단일 과업 집중에만 사용하고, 배경 상호작용을 막아야 한다.
- 긴급 공지는 공공 서비스 전반에서 같은 위치와 같은 시각 언어로 제공한다.
- 표는 데이터 비교가 목적이며, 행 전체나 데이터 셀을 불필요하게 대화형 요소로 만들지 않는다.

상태:

- 모달: open, closing, closed
- 아코디언/디스클로저: expanded, collapsed
- 탭: selected, unselected, focus
- 캐러셀: paused, playing, previous/next disabled
- 표: sortable, sorted ascending/descending, empty

접근성:

- 모달은 포커스 트랩, 초기 포커스, 닫기 후 포커스 복귀를 지원한다.
- 탭은 탭리스트, 탭, 탭패널 관계가 명확해야 한다.
- 캐러셀 자동 재생은 정지 수단을 제공해야 한다.
- 이미지에는 대체 텍스트 또는 숨긴 콘텐츠를 제공한다.

### 9.6 액션 컴포넌트

대상:

- 버튼
- 플로팅 버튼
- 링크

요구사항:

- 버튼은 기능 실행 또는 상태 변경에 사용한다.
- 링크는 위치 이동에 사용한다.
- 주요 행동의 중요도에 따라 primary, secondary, tertiary, danger, text 등 역할을 나눈다.
- 플로팅 버튼은 화면에서 가장 자주 사용하고 중요한 작업에 제한적으로 사용한다.

검수 기준:

- 버튼과 링크의 역할이 혼동되지 않는다.
- 아이콘 버튼에는 접근 가능한 이름이 제공된다.
- 비활성 상태는 왜 비활성인지 주변 맥락에서 이해 가능해야 한다.

### 9.7 선택 컴포넌트

대상:

- 라디오 버튼
- 체크박스
- 셀렉트
- 태그
- 토글 스위치
- 범위 슬라이더

요구사항:

- 라디오는 상호배타적 단일 선택에 사용한다.
- 체크박스는 다중 선택 또는 독립 동의에 사용한다.
- 셀렉트는 여러 옵션 중 하나를 선택할 때 사용하되, 옵션 수가 적으면 라디오가 더 적절할 수 있다.
- 토글은 즉시 적용되는 양자 상태에 사용한다.
- 범위 슬라이더는 선택 중 값이 계속 보이도록 한다.

접근성:

- 모든 선택지는 레이블을 가져야 한다.
- 그룹 레이블과 개별 레이블을 구분한다.
- 오류가 있을 경우 오류 메시지와 필드가 프로그램적으로 연결되어야 한다.

### 9.8 입력 컴포넌트

대상:

- 날짜 입력 필드
- 텍스트 영역
- 텍스트 입력 필드
- 파일 업로드

요구사항:

- 입력 필드는 레이블, 도움말, 예시, 필수 여부, 오류 메시지를 포함할 수 있어야 한다.
- 날짜 입력은 직접 입력과 달력 선택을 모두 고려한다.
- 파일 업로드는 허용 확장자, 용량, 개수, 업로드 상태, 삭제, 재시도를 제공한다.
- 텍스트 영역은 글자 수 제한과 현재 입력 수 표시를 지원할 수 있다.

상태:

- empty
- filled
- focus
- disabled
- readonly
- required
- error
- success
- loading/uploading

검수 기준:

- 입력 목적에 맞는 자동완성 속성을 제공한다.
- 오류는 색만으로 전달하지 않는다.
- 필수 입력 누락 시 오류 요약과 각 필드 오류가 함께 제공되는 것이 바람직하다.

### 9.9 피드백 컴포넌트

대상:

- 단계 표시기
- 스피너
- 토스트
- 스낵바

요구사항:

- 단계 표시기는 사용자가 거쳐야 하는 일련의 단계를 시각화한다.
- 스피너는 대기 상태를 표시하되 가능하면 대기 이유나 예상 시간을 함께 제공한다.
- 토스트는 사용자 행동 결과를 충분히 인지할 수 있는 시간 동안 보여준다.
- 스낵바는 흐름을 방해하지 않으면서 되돌리기 또는 다시 시도 같은 간단한 액션을 제공한다.

접근성:

- 상태 메시지는 스크린 리더가 인지할 수 있어야 한다.
- 로딩 상태가 길어지면 대체 안내를 제공한다.
- 자동으로 사라지는 메시지는 중요한 정보를 담지 않도록 한다.

### 9.10 도움 컴포넌트

대상:

- 도움 패널
- 따라하기 패널
- 맥락적 도움말
- 코치마크
- 툴팁
- 음성지원 TTS

요구사항:

- 도움은 사용자의 주 과업을 방해하지 않게 필요한 순간에 제공한다.
- 툴팁은 짧은 설명에만 사용하고, 필수 정보는 툴팁 안에만 숨기지 않는다.
- 코치마크는 새 기능 또는 복잡한 절차 안내에 사용한다.
- TTS는 시각 정보의 대체가 아니라 보완 수단으로 제공한다.

검수 기준:

- 도움말 트리거는 키보드와 터치에서 모두 사용할 수 있다.
- 도움 패널은 닫기, 포커스 이동, 본문 복귀가 자연스럽다.
- TTS 버튼은 읽을 대상과 현재 재생 상태를 명확히 제공한다.

### 9.11 설정/콘텐츠/모바일 컴포넌트

대상:

- 언어 변경
- 화면 크기 조정
- 접근 가능한 미디어
- 숨긴 콘텐츠
- 뒤로가기 버튼
- 바텀시트
- 수량 토글
- 탭바
- 스플래시 스크린

요구사항:

- 언어 변경은 한국어가 익숙하지 않은 사용자가 발견하기 쉬운 위치에 제공한다.
- 화면 크기 조정은 텍스트와 조작 요소의 가독성을 높이기 위한 핵심 접근성 기능이다.
- 숨긴 콘텐츠는 스크린 리더 사용자에게 필요한 설명을 제공한다.
- 모바일 컴포넌트는 작은 화면에서 핵심 탐색과 선택 과업을 빠르게 수행하게 해야 한다.

## 10. Figma 제작 요구사항

### 10.1 파일 구성

KRDS 공식 디자이너 가이드 기준, Figma 파일은 다음 페이지 구조를 가져야 한다.

- Style Guide
- Components
- Patterns
- Icons

작업 파일에서는 실무 운영을 위해 다음 페이지를 추가하는 것을 권장한다.

- 00 Cover
- 01 Usage Guide
- 02 Style Guide
- 03 Components
- 04 Basic Patterns
- 05 Service Patterns
- 06 Icons
- 90 QA Checklist
- 99 Archive

### 10.2 변수/스타일 구조

필수 variable collection:

- primitive: color, typo, number
- semantic: gap, padding, size-height, radius
- mode: color, border-width, shadow
- responsive: typo, layout-gap, card-padding

필수 mode:

- light
- high-contrast
- large
- small

운영 기준:

- Primitive는 직접 UI에 적용하지 않고 참조 기준으로 사용한다.
- Semantic은 실제 UI 의미에 맞게 적용한다.
- Component token은 코드에서 정의하고, Figma에서는 semantic 수준까지 관리한다.
- px 기반 Figma 값은 JSON 내보내기 후 CSS 환경에서 rem으로 변환하는 원칙을 유지한다.

### 10.3 오토레이아웃 기준

- 모든 버튼, 입력 필드, 태그, 배지, 알림, 카드형 컴포넌트는 Auto Layout을 기본으로 한다.
- 텍스트 길이 변화에 따라 가로/세로 확장이 예측 가능해야 한다.
- 최소 터치 영역은 모바일에서 44px 이상을 권장한다.
- 컴포넌트 내부 padding은 토큰을 사용한다.
- 임의 수치가 필요한 경우 `QA/exception note`에 사유를 기록한다.

### 10.4 네이밍 기준

컴포넌트명:

- 모두 소문자 사용
- 띄어쓰기는 언더바 사용
- 컴포넌트와 유형은 더블 언더바 사용
- 예시: `button__primary`, `text_input__error`

페이지/프레임명:

- 검색성을 위해 영문과 한글을 같이 사용
- 예시: `Main menu (메인 메뉴)`
- 영문 첫 글자만 대문자 사용

토큰명:

- 하이픈 구분자를 사용
- 시각 속성명보다 의미와 역할 중심으로 작성
- 예시: `color-background-primary`, `color-border-gray-light`

### 10.5 Figma QA 기준

- 모든 주요 컴포넌트는 light/high-contrast 모드에서 검수한다.
- 모든 텍스트 컴포넌트는 responsive large/small 모드에서 검수한다.
- 컴포넌트 property가 문서의 상태명과 일치한다.
- 모든 interactive component는 focus 상태를 포함한다.
- 버튼, 링크, 입력, 선택 컴포넌트에는 접근 가능한 이름을 설계 메모에 기록한다.
- 패턴 프레임은 구성 컴포넌트의 detach 없이 instance 조합으로 유지한다.

## 11. 개발 요구사항

### 11.1 패키지 제공

- NPM 패키지명: `krds-uiux`
- GitHub 저장소: `KRDS-uiux/krds-uiux`
- CDN 방식 제공
- HTML, CSS, JavaScript 기반 Component Kit 제공
- SCSS 원본과 컴파일 CSS 제공
- React/Vue 연계 문서 또는 Storybook 제공

### 11.2 토큰 연동

- Figma 토큰 JSON을 내보낸다.
- JSON을 CSS variable 형식으로 변환한다.
- CSS 변수는 `--krds` namespace를 기준으로 한다.
- 프로젝트별 재선언은 원본 코드 수정이 아니라 프로젝트 CSS/SCSS 레벨에서 처리한다.

### 11.3 코드 문서화

컴포넌트 상세 문서에는 다음이 필요하다.

- HTML 마크업
- CSS/SCSS import
- JavaScript 초기화 또는 이벤트 처리
- 상태 클래스
- 접근성 속성
- 키보드 조작
- 사용 예시
- 사용 금지 예시

## 12. 접근성 및 디지털 포용 요구사항

### 12.1 기준

KRDS는 KWCAG 2.2, WCAG 2.1/2.2, ARIA Authoring Practices Guide 등을 참조한다. 구성 요소별 접근성 가이드라인과 상호작용 가이드라인을 제공해야 한다.

### 12.2 필수 요구사항

- 모든 의미 있는 이미지에는 대체 텍스트 또는 숨긴 콘텐츠가 있어야 한다.
- 모든 입력 필드는 레이블과 오류 설명을 제공한다.
- 포커스 순서는 시각적/논리적 순서와 일치한다.
- 키보드만으로 주요 기능을 사용할 수 있다.
- 색상만으로 상태를 전달하지 않는다.
- 시간 제한이 있는 경우 조절 또는 연장 수단을 제공한다.
- 로그인 등 인증 과정은 인지 기능 테스트에만 의존하지 않는 방식을 제공한다.
- 화면 크기 조정, 선명한 화면 모드, 언어 변경, TTS 등 디지털 취약계층 지원 기능을 제공한다.

### 12.3 화면별 접근성 체크

| 화면/기능 | 체크 항목 |
|---|---|
| 메인 | 히어로/카드/CTA의 heading 구조, 카드 링크 목적, 이미지 대체 |
| 검색 | 포커스 이동, 결과 수 안내, 결과 없음 안내 |
| 전체메뉴 | 메뉴 구조, 현재 위치, Esc 닫기, 배경 포커스 차단 |
| 글자·화면 설정 | 선택 상태, 즉시 반영, 초기화, 고대비 |
| 컴포넌트 상세 | 예제 코드의 label, role, state, keyboard 명시 |
| 입력 폼 패턴 | 오류 요약, 필드별 오류 연결, 자동완성 |
| 로그인 패턴 | 접근 가능한 인증, 초점 순서, 세션 연장 |
| 신청 패턴 | 현재 단계 안내, 섹션 제목, 제출 전 확인 |

## 15. 인수 기준

### 15.1 문서 웹사이트

- 모든 1차 메뉴와 하위 문서가 접근 가능하다.
- 통합검색, 전체메뉴, 글자·화면 설정이 모든 주요 화면에서 동작한다.
- 역할별 시작하기가 실제 산출물 링크로 연결된다.
- 컴포넌트와 패턴 페이지에 사용 기준, 상태, 접근성, 코드가 포함된다.

### 15.2 Figma 라이브러리

- Pretendard GOV 기준 텍스트 스타일이 설정되어 있다.
- primitive, semantic, mode, responsive variable collection이 구성되어 있다.
- 컴포넌트는 variant/property 기반으로 관리된다.
- 기본 패턴 11종과 서비스 패턴 5종이 instance 조합으로 구성된다.
- light/high-contrast와 large/small 모드에서 검수된다.

### 15.3 개발 키트

- NPM, GitHub, CDN 설치 방식이 동작한다.
- SCSS/CSS, JS 적용 예제가 제공된다.
- Figma 토큰 JSON과 CSS variable 변환 방식이 문서화되어 있다.
- 컴포넌트 상태와 접근성 속성이 구현되어 있다.

## 16. 결론

KRDS는 단순 UI Kit이 아니라 공공 디지털 서비스의 설계, 개발, 검수, 운영을 하나의 기준으로 묶는 디자인 시스템 플랫폼이다. 웹사이트는 학습과 문서화 허브, Figma는 설계 생산성의 중심, HTML Component Kit과 GitHub/NPM은 개발 적용의 중심, 디자인 토큰은 세 영역을 연결하는 공통 언어로 기능한다.

역기획 관점에서 가장 중요한 설계 요구는 `역할별 온보딩`, `문서형 정보 구조`, `컴포넌트 상태/접근성 명세`, `토큰 기반 Figma-코드 연결`, `디지털 포용 기능의 제품화`다. 특히 화면/컴포넌트 요구사항은 단순 목록이 아니라 실제 공공 서비스 과업을 완수하게 하는 패턴과 서비스 여정으로 연결되어야 한다.
